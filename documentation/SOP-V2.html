DYPERF ERP — V2 Roadmap

Submission rewiring · Storage · UX · Migration

0 · What this document is

V1 (SOP.html) described the system as built. This document describes the system as it must become after the client meeting that settled how submissions actually work. It is a build roadmap, not a manual: every module gets a current-state → target-state → change list → acceptance criteria block you can hand straight to a developer.

This application is live with real scholars in Batch Dec 2025. Every instruction in this document is written for a production system. The governing rule is additive-only, zero deletion — we add columns, tables and code paths; we never drop a column, drop a table, or delete a row. Legacy shapes stay readable behind compatibility views until the new path is proven.

2 · Target data model

Additive only. Nothing below drops or destroys anything. Run in the order given.

2.1 · Rename milestones to targets, without moving data

The existing progress_reports table is, in V2 language, the targets table — it already holds per-scholar, per-semester named items with a completion percentage. Rename it and leave a view behind so any code path we miss keeps working during the deploy window.

-- Rename in place: zero data movement, zero downtime, fully reversible.
ALTER TABLE progress_reports RENAME TO targets;

-- Backward-compatibility view so old code/queries keep working mid-deploy.
-- Drop this only after the frontend and all services are cut over.
CREATE OR REPLACE VIEW progress_reports AS SELECT * FROM targets;

-- Target-specific columns
ALTER TABLE targets
  ADD COLUMN IF NOT EXISTS requires_file  BOOLEAN DEFAULT TRUE,
  ADD COLUMN IF NOT EXISTS is_mandatory   BOOLEAN DEFAULT TRUE,
  ADD COLUMN IF NOT EXISTS order_index    INTEGER DEFAULT 0,
  ADD COLUMN IF NOT EXISTS created_by     UUID REFERENCES users(id),
  ADD COLUMN IF NOT EXISTS approved_at    TIMESTAMP,
  ADD COLUMN IF NOT EXISTS approved_by    UUID REFERENCES users(id);

-- module_name is the target's name. Keep the column (data lives there);
-- the UI labels it "Target name". Do NOT rename it — production rows depend on it.
COMMENT ON COLUMN targets.module_name IS 'Target name — displayed as "Target" in the UI';
Why a view and not a straight rename. The frontend, the notify service and the dashboard all query progress_reports. A view means the rename can ship in one migration while the application cuts over across several deploys, and a rollback is a single ALTER TABLE targets RENAME TO progress_reports;.

2.2 · Progress report cycles

CREATE TABLE IF NOT EXISTS progress_report_cycles (
  id           UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  batch_id     UUID NOT NULL REFERENCES batches(id) ON DELETE RESTRICT,
  semester     INTEGER NOT NULL,
  title        VARCHAR(255) NOT NULL,           -- "Progress Report — Semester 1"
  description  TEXT,
  opens_at     DATE,
  due_date     DATE,
  status       VARCHAR(12) NOT NULL DEFAULT 'open',   -- open | closed
  created_by   UUID REFERENCES users(id),
  created_at   TIMESTAMP DEFAULT NOW(),
  updated_at   TIMESTAMP DEFAULT NOW(),
  UNIQUE (batch_id, semester)
);
CREATE INDEX IF NOT EXISTS idx_pr_cycles_batch ON progress_report_cycles(batch_id);

Cycles are created automatically in three places: when a batch is created (cycle for semester 1), when the V1 semester advance action runs (cycle for the new semester), and by a backfill for every existing active batch at migration time.

2.3 · Submissions gains a kind and its links

-- New submission kind
ALTER TYPE submission_type ADD VALUE IF NOT EXISTS 'target';

ALTER TABLE submissions
  ADD COLUMN IF NOT EXISTS cycle_id      UUID REFERENCES progress_report_cycles(id),
  ADD COLUMN IF NOT EXISTS target_id     UUID REFERENCES targets(id),
  -- Snapshot of which approval model applied at submit time, so changing a
  -- batch's config later never rewrites the history of a submission already in flight.
  ADD COLUMN IF NOT EXISTS workflow_kind VARCHAR(12),      -- none | single | chain
  -- Migration bookkeeping (D1). Never deleted, only flagged.
  ADD COLUMN IF NOT EXISTS merged_into_id UUID REFERENCES submissions(id),
  ADD COLUMN IF NOT EXISTS legacy_flag    VARCHAR(24);     -- 'pre_v2' | 'merged_source'

-- One submission per scholar per cycle, and per scholar per target.
CREATE UNIQUE INDEX IF NOT EXISTS uq_sub_cycle
  ON submissions (cycle_id, student_user_id) WHERE cycle_id IS NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS uq_sub_target
  ON submissions (target_id, student_user_id) WHERE target_id IS NOT NULL;
This closes the duplicate hole. Namita's three "Progress Report 1" rows happened because the only uniqueness guard in the system covers assignment_id, which is NULL for progress reports. The two partial unique indexes above make that impossible from now on, while leaving the existing duplicate rows untouched for the merge tool to reconcile.

2.4 · File slots

Progress reports need two named files, not two arbitrary ones. Slots live in the existing file_urls descriptor and on the media row.

ALTER TABLE videos
  ADD COLUMN IF NOT EXISTS slot        VARCHAR(24),        -- report | presentation | attachment
  ADD COLUMN IF NOT EXISTS batch_id_ref UUID REFERENCES batches(id),  -- folder taxonomy
  ADD COLUMN IF NOT EXISTS semester    INTEGER,
  ADD COLUMN IF NOT EXISTS preview_key TEXT,               -- derived PDF preview object
  ADD COLUMN IF NOT EXISTS checksum    VARCHAR(64),
  ADD COLUMN IF NOT EXISTS verified_at TIMESTAMP;          -- HEAD-verified in Zata

The descriptor appended to submissions.file_urls becomes:

{ "name": "Progress Report 1", "media_id": "…", "slot": "report",
  "type": "pdf", "size": 2481293, "uploaded_at": "2026-08-15T…" }

2.5 · Two workflows per batch

batches.approval_config currently holds { "stages": [...] } — a single chain used for everything. V2 needs one config per submission kind, with the old shape still readable.

{
  "version": 2,
  "assignment":      { "mode": "none" },
  "progress_report": { "mode": "chain",  "stages": [
      { "name":"coordinator",     "label":"Coordinator",     "type":"role",          "role":"coordinator",  "order_index":1 },
      { "name":"academic_guide",  "label":"Academic Guide",  "type":"student_guide", "guide_type":"academic",  "order_index":2 },
      { "name":"industry_mentor", "label":"Industry Mentor", "type":"student_guide", "guide_type":"industry",  "order_index":3 }
  ]},
  "target":          { "mode": "single", "approver":
      { "name":"target_review", "label":"Target Review", "type":"role", "role":"coordinator", "order_index":1 }
  }
}
-- Reader shim in submissions.service.js — production batches carry the v1 shape.
const readWorkflow = (cfg, kind) => {
  if (!cfg) return DEFAULTS[kind];
  if (cfg.version === 2) return cfg[kind] ?? DEFAULTS[kind];
  // v1 shape: { stages: [...] } was always the progress-report/mandatory chain
  if (kind === 'progress_report') return { mode:'chain', stages: cfg.stages?.length ? cfg.stages : DEFAULTS.progress_report.stages };
  if (kind === 'assignment')      return { mode:'none' };
  return DEFAULTS.target;
};

2.6 · Document-style feedback

Progress-report feedback is a page of prose, not a comment. Keep comments as the plain-text mirror (emails, list previews, exports) and add a rich field for the document view.

ALTER TABLE approvals
  ADD COLUMN IF NOT EXISTS feedback_html TEXT,        -- Tiptap output, the document view
  ADD COLUMN IF NOT EXISTS feedback_updated_at TIMESTAMP;
-- comments stays authoritative for plain text; the service writes both,
-- deriving comments from feedback_html when only the rich field is supplied.
Tiptap 3 is already a dependency (used by the rich-text editor elsewhere), so the document-style feedback editor needs no new package.

2.7 · Media folder taxonomy

ALTER TABLE media_folders
  ADD COLUMN IF NOT EXISTS batch_id   UUID REFERENCES batches(id) ON DELETE CASCADE,
  ADD COLUMN IF NOT EXISTS semester   INTEGER,
  ADD COLUMN IF NOT EXISTS kind       VARCHAR(24),   -- assignments | progress_reports | targets | lectures | formats
  ADD COLUMN IF NOT EXISTS is_system  BOOLEAN DEFAULT FALSE;  -- auto-created, not user-deletable

Auto-created tree, mirrored exactly by the Zata object key so the bucket is browsable and the Media UI matches storage one-for-one:

Media UI folder tree Zata object key ──────────────────────── ────────────────────────────────────────────── ABRF-2024/ ABRF-2024/ Batch Dec 2025/ BATCH-DEC-2025/ Semester 1/ sem-1/ Assignments/ assignments/{submissionId}/{file} Progress Reports/ progress-reports/{submissionId}/{slot}-{file} Targets/ targets/{submissionId}/{file} Lectures/ lectures/{mediaId}/{file} Formats/ formats/{mediaId}/{file}
Existing objects keep their existing keys. The key is stored on the media row, so old files continue to resolve. The new taxonomy applies to new uploads only; a backfill job can optionally re-file old rows into the right folder without touching the object at all.

3 · Migration plan (zero deletion)

Six ordered steps. Each is reversible. Nothing runs against production until the step before it has been verified on a Neon branch restored from the production snapshot.

Step 0 · before anything

Snapshot and baseline ◐ done on the verification branch — repeat on live

  1. Take a Neon point-in-time branch of production. Name it pre-v2-<date>.
  2. Run documentation/diagnostics/audit-submissions.sql against production and save the output of query 10 — those counts are the contract. After migration every count must be equal or greater. None may ever fall.
  3. Export submissions, approvals, submission_remarks and videos to CSV and store them outside the database.
Step 1 · schema only, no behaviour change

Apply the additive DDL ✔ written & verified

Everything in Section 2, added to backend/src/db/alter.js as new numbered blocks. After this step the application behaves exactly as before — new columns are unused, the compatibility view keeps progress_reports queries working.

Verify: app boots · every existing screen loads · query 10 counts unchanged.
Rollback: ALTER TABLE targets RENAME TO progress_reports; DROP VIEW …; and drop the added columns. No data touched.

Step 2 · backfill, still no behaviour change

Create cycles and classify legacy rows ✔ written & verified

-- 2a. One progress-report cycle per active batch per semester reached so far.
INSERT INTO progress_report_cycles (batch_id, semester, title, due_date, status, created_by)
SELECT b.id, s.sem,
       'Progress Report — Semester ' || s.sem,
       NULL,
       CASE WHEN s.sem = MAX(be.current_semester) THEN 'open' ELSE 'closed' END,
       NULL
FROM batches b
JOIN batch_enrollments be ON be.batch_id = b.id AND be.status = 'active'
CROSS JOIN LATERAL generate_series(1, GREATEST(be.current_semester,1)) AS s(sem)
GROUP BY b.id, s.sem
ON CONFLICT (batch_id, semester) DO NOTHING;

-- 2b. Mark every pre-existing submission so the UI can tell old from new.
UPDATE submissions SET legacy_flag = 'pre_v2' WHERE legacy_flag IS NULL;

-- 2c. Stamp the workflow that was actually used, so history reads correctly.
UPDATE submissions SET workflow_kind =
  CASE WHEN submission_type = 'assignment' AND EXISTS
            (SELECT 1 FROM approvals a WHERE a.submission_id = submissions.id)
       THEN 'chain'                       -- old assignments DID go through approval
       WHEN submission_type = 'assignment' THEN 'none'
       ELSE 'chain' END
WHERE workflow_kind IS NULL;

-- 2d. Attach legacy progress reports to their semester's cycle.
UPDATE submissions s SET cycle_id = c.id
FROM progress_report_cycles c
WHERE s.submission_type = 'progress_report'
  AND s.cycle_id IS NULL
  AND c.batch_id = s.batch_id
  AND c.semester = s.semester;
2d will violate the new unique index for Namita and Satish, who have more than one progress report in the same semester. That is intentional and it is the trigger for Step 3 — create the unique indexes after the merge, not before. Sequence: run 2d, then Step 3, then create uq_sub_cycle.
Step 3 · the merge (D1)

Pair split reports into one record ◐ tool built — not yet run

The merge is proposed by a script and confirmed by a human. It never runs unattended.

  1. Proposescript · dry run Group progress_report submissions by (student, batch, semester). Where a group has more than one row, classify each by title and file type: a row whose file is PPT/PPTX or whose title matches /present|slide|ppt/i is the presentation; the other is the report. Output a proposal CSV. Nothing is written.
  2. ReviewCoordinator · one-time screen A Review merged reports page lists each proposed pair side by side with both files previewable, and Accept / Split / Skip per row. This is the manual gate D1 asks for.
  3. Applyscript · transactional, per pair For each accepted pair: choose the survivor (the row that carries approvals; if both do, the earliest submitted). Move the other row's media rows onto the survivor with the correct slot, append its descriptor to the survivor's file_urls, re-parent its submission_remarks, and copy any approval comments into the survivor's feedback. Then set the source row's merged_into_id = survivor and legacy_flag = 'merged_source'.
    The source row is never deleted. It is hidden from the default UI by WHERE merged_into_id IS NULL and remains fully queryable, with its approvals and audit history intact.
  4. Create the guardsmigration Only now create uq_sub_cycle and uq_sub_target. If either fails, an unmerged duplicate remains — fix it and retry.
Step 4 · abandoned drafts

Hide, do not delete ○ UI filter pending

The two empty drafts ("PPPP", "PROGRESS REPORT") and any like them stay in the table. The student UI filters them out with WHERE NOT (status='draft' AND file_count=0 AND created_at < NOW() - INTERVAL '30 days'), and an admin Abandoned drafts view lists them so staff can see what a stuck scholar tried to do.

Step 5 · cutover

Flip the reads, module by module ◐ flag in place

Behind a single environment flag V2_SUBMISSIONS=true, each module switches from the legacy path to the V2 path in the order given in Section 7. The flag can be turned off at any point and the application returns to V1 behaviour, because no V1 data was removed.

Step 6 · retire the shims

Only after two clean weeks ○ pending

Drop the progress_reports compatibility view, remove the v1 approval_config reader shim, and archive the merge tooling. Keep merged_into_id, legacy_flag and every legacy row permanently.

4 · Module-by-module change spec

Fourteen modules. Each block: what it does today, what it must do, the backend and frontend work, and how you know it is done.

M1✔ Backend done

Submissions core — one table, three behaviours

Rewire
Today

submitForReview() builds an approval chain for every submission. Depth is decided only by whether the linked assignment is optional. Assignments therefore go through approval, which the client does not want.

V2

The submission's kind decides the workflow, read from the batch's per-kind config and snapshotted onto the row as workflow_kind. Assignment = none, Progress report = chain, Target = single.

Backend

  • Refactor submitForReview() into resolveWorkflow(submission, batch) + createApprovalRows(stages). For mode:'none' create no approval rows at all and leave the submission at submitted as a terminal state.
  • Add the v1→v2 approval_config reader shim (§2.5) so production batches keep working.
  • Validation at submit time, per kind: assignment needs ≥1 file; progress report needs both slots filled; target needs ≥1 file when requires_file.
  • Guide-resolution fallback (fixes V1 G-03): if a student_guide stage cannot resolve to a user, still write reviewer_role so the stage is actionable by role instead of being invisible, and raise a staff notification.

Frontend

  • Retire the generic /student/submit catch-all page. Submission always starts from the thing being submitted against — an assignment, a cycle, or a target.
  • StatusBadge gains a terminal Received state for assignments so scholars are not left waiting for an approval that will never come.

Acceptance

  • Submitting an assignment creates zero rows in approvals.
  • Submitting a progress report creates exactly the batch's configured chain.
  • Submitting a target creates exactly one approval row.
  • A scholar with no assigned guide can still have their report reviewed — the stage falls back to role.
M2◐ Backend done · UI pending

Assignments — no approval, many files, full page, preview

Change
Today

Assignment list only. "Submit" bounces the scholar to a generic form at /student/submit?assignment=…. One file at a time, PDF/PPT/PPTX only, 25 MB. Goes through an approval chain. No preview anywhere.

V2

Clicking an assignment opens its own full page. Multiple files of mixed type, each previewable inline the moment it uploads. Submit is terminal — received, no approval, no feedback.

Backend

  • New routes: GET /assignments/:id (detail incl. my submission) and GET /assignments/:id/my-submission.
  • Widen the attachment MIME allow-list for assignment and target kinds: pdf, ppt, pptx, doc, docx, xls, xlsx, png, jpg, zip. Keep magic-byte sniffing for every type — do not weaken that check, extend the family map.
  • Raise the per-file cap to 50 MB and add a per-submission aggregate cap (suggest 200 MB), both configurable per course so it maps to what you bill.
  • Drop the status = 'draft'-only restriction on attachment upload for assignments so a scholar can add a file to a submission they have started, and allow file removal before submit (a delete that removes the Zata object and the media row inside one transaction).

Frontend

  • New route /student/assignments/:id — brief, due date, mandatory flag, file dropzone, inline preview strip, Submit.
  • New route /admin/assignments/:id — brief, roster of who has and has not submitted, per-scholar preview, bulk export.
  • Assignment cards show Pending / Submitted / Overdue, not an approval status.

Acceptance

  • A scholar can attach five files of three different types, preview each, remove one, and submit.
  • The assignment detail page shows the submitted/pending split for the whole batch at a glance.
  • No approval row and no reviewer email is ever produced by an assignment.
M3◐ Backend done · UI pending

Progress Reports — cycles, two slots, chain, document feedback

Rewire
Today

A free-form submission type. Students file the report and the slides as two separate submissions, repeatedly, because nothing pairs them and nothing stops duplicates. Feedback is a small comment box.

V2

One cycle per batch per semester. One submission per scholar per cycle, holding exactly two named files. Three-stage review, each stage writing a page of document-style feedback.

Backend

  • CRUD for progress_report_cycles; auto-create on batch creation and on semester advance.
  • GET /progress-reports/cycles?batch_id= and GET /progress-reports/my-cycle.
  • Slot-aware upload: the attachment endpoint takes slot=report|presentation, validates the MIME against the slot (report → PDF only, presentation → PPT/PPTX only), and replaces rather than appends when a slot is re-uploaded — the superseded media row is retained and marked, not deleted.
  • Submit blocked with a clear message until both slots are filled.
  • PATCH /approvals/:id/feedback — save feedback_html as a draft without taking the stage action, so a reviewer can write over two sittings.

Frontend

  • /student/progress-reports/:cycleId — two clearly-labelled slots, each with its own dropzone, accepted-type hint, preview and replace action.
  • /admin/submissions/:id/review — the full-page review screen: document viewer on the left (≈60%), stage feedback on the right (≈40%).
  • Feedback editor: Tiptap, borderless, full-height, serif, generous line-height — it should read as a page of writing, not a form field. Autosave every few seconds into feedback_html. Previous stages' feedback shown above, read-only, in the same document style.

Acceptance

  • A scholar cannot submit with one slot empty, and cannot create a second submission for the same cycle.
  • Re-uploading the presentation replaces it; the superseded file is still in storage and still audit-visible.
  • A reviewer can write a page of feedback, leave, come back, and it is still there unsent.

M7◐ Backend done · UI pending

Storage — Zata as the single source of truth

Critical
Today — and why media won't fetch

proxyUpload writes to the server's local disk first, then fires the Zata upload as unawaited background work whose failure is only a console.warn. The read path checks local disk first, Zata second. On a host with ephemeral disk the file disappears on the next deploy or restart, the DB row still claims it exists, and Zata may never have received it. That is precisely "it stores but it doesn't fetch".

V2

Every upload goes to Zata synchronously and is HEAD-verified before any DB row is written. A failed upload fails loudly with nothing left behind. Local disk becomes an optional read cache that can be wiped at any time with no consequence.

Why submission attachments already work and media does not

Worth noting because it is the proof the fix is right: uploadSubmissionAttachment already does it correctly — it awaits s3.uploadFile, and if the DB write fails it deletes the object it just uploaded. That path is transactional. proxyUpload is not. Make proxyUpload behave like uploadSubmissionAttachment.

Backend changes

  • Invert the write order. await s3.uploadFile(...) → await s3.headObject(...) to confirm size → write the media row with upload_status='ready' and verified_at=NOW(). Only then, optionally, populate the local cache.
  • Fail loudly. If Zata errors, return 502 with the real reason and write nothing to the database. A media row must never exist without a verified object behind it.
  • Invert the read order. Zata first; local only when STORAGE_LOCAL_CACHE=true and the cached file's size matches videos.file_size.
  • Boot check. If NODE_ENV=production and Zata is not configured, refuse to start rather than silently degrading to a local-disk mode that will lose data.
  • Reconciliation job. Nightly: HEAD every videos row's object. Mark upload_status='missing' on failure. Never delete the row — the record of what was uploaded is itself valuable.
  • Orphan sweep. List the bucket, compare against videos.object_key, report objects with no row (billed but unreferenced). Report only; deletion is always a human decision.
  • Key builder. Replace buildVideoKey(courseCode, videoId, filename) with the taxonomy-aware builder from §2.7.
Ship this first, today: the crypto bug. backend/src/modules/videos/videos.controller.js line ~459 calls crypto.randomUUID(), but crypto is never imported in that file. The global Web Crypto object is only unflagged from Node 19 — and backend/package.json declares "node": ">=18". If the host runs Node 18 this throws ReferenceError on every submission attachment upload, surfacing in the UI as "Upload failed". Fix: import crypto from 'crypto'; at the top of the file (as videos.service.js already does), or use the uuid package that is already a dependency. Then confirm the host's Node version.

Storage health & billing

  • New admin page /admin/storage: per-course usage in bytes and file count, split by lectures / formats / submissions; a quota bar against the plan you sold; and a health panel listing pending, missing and orphaned objects.
  • Query 8 of the diagnostics SQL is the exact aggregate this page renders — the number you invoice on.
  • Per-course quota stored in courses.preferences.storage_quota_bytes; uploads warn at 80% and block at 100% with a message naming the course.

Acceptance

  • Pulling the local storage/ directory entirely has no effect on any playback or download.
  • Uploading with Zata credentials deliberately broken produces a clear error and leaves no media row.
  • The reconciliation job on the current production data reports a precise list of files that exist in the database but not in the bucket — that list is your recovery worklist.

The problem

Files today are private and reachable only through a session-token stream that sets Content-Disposition: attachment — a download, never a view. Reviewers therefore download a PDF, open it in another app, then come back to type feedback. That is the single biggest friction in the whole reviewing experience.

5 · UX & information architecture

This is the suggestion track you asked for. The governing principle: a coordinator should never have to remember where something lives. There is one place for people, one place for academic work, one place for review. Everything else is a tab, a filter or a drawer inside those.

Five rules the redesign follows

  1. One object, one homeKills duplicate tables Anything about a scholar lives on the scholar. There is no student list inside Progress Reports and another inside Targets — there is the scholar list, and the scholar page has tabs.
  2. Sidebar is for destinations, pages are for work9 items, not 20 If two menu items always lead to the same mental task, they are tabs on one page, not two entries.
  3. Drawer for looking, page for doingLeast clicks Reading a list, checking a status, recording a payment — drawer, stay in context. Reading a document and writing a page of feedback — full page, no distractions.
  4. Every count is a linkNo dead numbers "3 pending" on a dashboard tile opens the scholar list already filtered to those three. A number you cannot click is a number that makes someone go searching.
  5. Filter state lives in the URLShareable A coordinator can send a guide a link to exactly the view they are describing.

9 · Acceptance test script

Run this end to end on a test batch before each phase reaches production. It is deliberately written as actions, not assertions, so a non-developer can execute it.

A · Assignments (no approval)

  1. Coordinator creates an assignment, due in 3 days, mandatory, published.
  2. Scholar's dashboard shows it as Pending; the scholar list shows the pending count increase by one.
  3. Scholar opens the assignment's own page, uploads a PDF, a DOCX and a PNG, and previews all three inline.
  4. Scholar removes the PNG — it disappears from the list and from the bucket.
  5. Scholar submits. Status reads Received. Verify: zero rows in approvals for it.
  6. No reviewer receives any email.
  7. The assignment's admin page shows 1 submitted / N pending.

B · Progress reports (3-layer + document feedback)

  1. Advance a test batch to a new semester; confirm a cycle was created automatically with the right title.
  2. Scholar opens the cycle. Submit is disabled with both slots empty.
  3. Upload a PPTX into the Progress Report slot — rejected, PDF only.
  4. Upload the PDF into Progress Report and the PPTX into Presentation. Submit is now enabled.
  5. Attempt a second submission for the same cycle — blocked by the unique index with a clear message.
  6. Coordinator opens the review page, reads both files without downloading, writes half a page, closes the tab.
  7. Reopen — the feedback is still there, unsent. Finish it and approve.
  8. Academic guide receives the stage email; their screen shows stage 1's feedback above their own.
  9. Industry mentor approves. Scholar receives the approval email with the full feedback.

C · Targets

  1. Coordinator creates a set of 6 targets and applies it to the whole batch in one action.
  2. Scholar profile shows 0/6, 0%.
  3. Scholar submits against one target with a file and a note.
  4. Exactly one approval row is created, assigned to the configured approver.
  5. Approver rejects with feedback — the scholar sees it and resubmits.
  6. Approver approves. Profile now reads 1/6, 17%.

D · Storage

  1. Break the Zata credentials deliberately. Upload → clear error, and no media row is created.
  2. Restore credentials. Upload → file appears in the bucket under the course/batch/semester path, and in the Media UI in the matching folder.
  3. Delete the server's local storage/ directory entirely. Every preview, stream and download still works.
  4. Run the reconciliation job — it reports exactly the rows whose objects are missing.

  1. Re-run query 10 of the diagnostics. Every count equal or higher than the pre-migration baseline.
