For staffSOPs

For the build teamGap audit

1 · The complete software lifecycle

Read this section top to bottom once. Everything else in this manual is a zoom-in on one of these phases. Time markers assume a standard 24-month, 4-semester fellowship.

P0 Setup→ P1 Admissions→ P2 Enrolment→ P3 Sem 1→ Sem 2→ Sem 3→ Sem 4→ P4 Completion

Phase 0 — One-time institutional setup

Who: Admin only. When: before any applicant is touched. Where: /admin/wizard (six tabs) plus /admin/settings.

  1. Configure email deliveryAdmin · /admin/settings Enter the Brevo API key / sender name / sender email, then use Send test email. Nothing else in the system works properly until this is green — candidate credentials, shortlist letters, approval alerts and fee reminders all ride on it. GET /settings/email/effective tells you whether the server is in live or mock mode.
  2. Brand the portalAdmin · /admin/settings Upload light and dark logos (data-URL, under 500 KB each) and set the UI labels — this is where "Student" becomes "Scholar" across every screen for every role.
  3. Create the courseAdmin · /admin/wizard → Courses Name, code, duration (24 months), max students per batch, and the fee structure as a per-semester map, e.g. {"1":50000,"2":50000,"3":50000,"4":50000}. Course preferences also decide which modules appear for that course.
  4. Create the batchAdmin / Coordinator · /admin/batches A batch belongs to one course and carries start date, end date, seat cap and status (upcoming → active → completed). Every scholar, fee, submission, assignment and progress report hangs off a batch — a batch is the real unit of operation.
  5. Define the approval workflow for that batchAdmin · /admin/wizard → Workflows This writes batches.approval_config.stages. Default is the classic three layers: Coordinator (role) → Academic Guide (the scholar's own guide) → Industry Mentor (the scholar's own mentor). You can add, remove or reorder stages, or point a stage at a specific user. Set this before the first submission — the chain is snapshotted at submit time.
  6. Create staff accounts and assign rolesAdmin · /admin/users, /admin/roles Create the coordinator, guides and mentors. Assign each a role scoped to the course or batch. Then send credentials (POST /users/:id/send-credentials, or bulk from the wizard).
  7. Tune notification rulesAdmin · /admin/wizard → Notifications Per event, choose channel and receivers. Instant events (application received, test completed, stage opened, approved, needs revision) fire on the action; scheduled events (fee_due, deadline_overdue) are swept daily by the queue worker.
  8. Build the entrance testAdmin / Coordinator · /admin/test-builder Create the test (duration, total marks, passing marks, instructions), add sections and questions (MCQ, true/false, short, long, file upload), optionally set pick_count per section for randomised question sets — then Publish. A draft test cannot be assigned.
  9. Upload formats and lecturesAdmin / Coordinator · /admin/formats, /admin/lectures Formats are the downloadable templates (progress report format, thesis chapter format…). Lectures are the media library, organised in folders, streamed to scholars through signed sessions.
Done-when check for Phase 0: test email delivered · course exists with a fee map · batch exists and is active · approval_config saved · coordinator can log in and sees Applicants · entrance test shows status published.

Phase 1 — Admissions pipeline

Who: Coordinator drives it, Admin supervises. Where: /admin/applicants (list view or Kanban board). Duration: typically 6–10 weeks per intake.

Applied→ Shortlisted for Test→ Test Sent→ Test Submitted→ Final Shortlist→ Registration Fee Paid→ Enrolled ·Rejected (side branch, any stage)
  1. Candidate appliesPublic · /apply Multi-step public form → POST /public/applications (rate-limited, body-size capped). Creates an applicants row at status submitted. Two emails fire: application_submitted to the candidate and application_submitted_staff to whoever the notification rules name. Candidate lands on /confirmation.
    Alternative: Coordinator bulk-imports candidates from Excel via the Import drawer on /admin/applicants, or adds one manually.
  2. Screen the applicationCoordinator · Applied column Open the card, read PhD details, discipline, thesis title, Scopus publications, research statement. Then either Shortlist for Test (→ shortlisted_test) or Reject (a remark is mandatory; the system records which stage they were rejected from).
  3. Send the testCoordinator · Shortlisted for Test column Click Send Test, pick the published test → POST /tests/:id/assign. The system creates a candidate login, generates a password, and emails the test_credentials template with the login URL, username, password, duration and section list. Status → test_pending.
    Column-level bulk action: Remind everyone who hasn't started sends test_reminder to the whole column.
  4. Candidate takes the testCandidate · /test-login → /test/:id/instructions → /test/:id Logs in with the emailed credentials (POST /test-auth/login), reads instructions, starts (POST /tests/:id/start — this stamps started_at and freezes the question set), answers with periodic autosave (PATCH /tests/:id/autosave), submits (POST /tests/:id/submit). MCQ and true/false auto-score. Status → test_completed. Emails: test_completed to the candidate, test_completed_staff to staff.
    The Kanban shows a live Test in progress badge while an attempt is inside its time window. If a candidate is locked out (browser crash, power cut), the coordinator uses Reset attempt — that is the only supported recovery.
  5. Review scores and decideCoordinator / Admin · Test Submitted column Open /admin/applicants/:id/test-results to see per-question responses, award marks on descriptive answers, and see pass/fail against passing_marks. Then Final Shortlist or Reject.
  6. Final shortlist → registration feeCoordinator · Final Shortlist column Moving to shortlisted automatically emails applicant_shortlisted — the interview-qualified letter that carries the registration fee amount and bank details. The column has a bulk Payment reminder action (applicant_shortlist_payment_reminder) with a 24-hour per-candidate cooldown so nobody gets spammed.
  7. Mark the fee receivedCoordinator · Final Shortlist column When the transfer lands, tick the candidates and Mark as paid → status payment_received. This is a manual reconciliation step against the bank statement — there is no payment gateway in the loop.
  8. Convert to scholarCoordinator / Admin · Registration Fee Paid column Convert to student → POST /applicants/:id/convert. In one transaction the system: creates the users row (or reuses the test account), generates a fresh password, creates the batch_enrollments row with an enrolment number and current_semester = 1, grants the student role scoped to that batch, and flips the applicant to enrolled. Credentials are then emailed via login_credentials.
The Rejected column is reversible. A rejected candidate keeps the stage they were rejected from, so the Rejected tab can be filtered by origin, and Reconsider puts them back into the pipeline with the from-stage marker cleared. Rejection remarks are mandatory and permanent — treat them as the official record.

Phase 2 — Onboarding a new scholar (week 0)

Conversion creates the account. It does not create everything the scholar needs. This checklist is what turns a raw account into a working scholar, and several of its steps are manual today (see the gap audit).

Do not skip step 2 and 3. The approval chain resolves the Academic Guide and Industry Mentor stages from student_guides at the moment of submission. If no guide is assigned, the stage is created with an empty reviewer and the submission silently stalls after coordinator approval. This is the single most likely day-one production failure.

Phase 3 — The academic engine (repeats × 4 semesters)

Semesters 1 → 4 are structurally identical. Everything below repeats each semester; only the semester number on assignments, fees, progress reports and submissions changes.

3a · Setting up a semester

  1. Publish the semester's assignmentsCoordinator · /admin/assignments Per batch, per semester: title, description, due date, and two switches that matter — Mandatory and Published. Mandatory assignments run the full approval chain; optional ones need only a single coordinator approval. Unpublished assignments are invisible to scholars.
  2. Raise the semester feeCoordinator · /admin/fees Create a fee per scholar: batch, semester, amount, due date. The scheduled fee_due scan starts nudging 7 days before the due date and repeats every 3 days.
  3. Define progress milestonesCoordinator · /admin/progress Per scholar, per semester: a named module (e.g. "Literature Review"), description and due date, starting at not_started / 0%.
  4. Load lectures and formats for the semesterCoordinator · /admin/lectures, /admin/formats Media can be scoped course-wide or to a single batch; visibility is enforced server-side.

3b · The scholar's working loop

  1. Sign in and read the dashboardScholar · /student/dashboard Pending assignments, submission statuses, fee position, unread notifications.
  2. Download the formatScholar · /student/formats Always draft against the current template — reviewers reject on format.
  3. Attend / watch lecturesScholar · /student/lectures Streamed through a signed session; watch progress is logged and visible to staff analytics.
  4. Submit the workScholar · /student/assignments → Submit, or /student/submit One submission per assignment, enforced by a DB unique index. Attach the file, then Submit for review. A progress report cannot be submitted without a verified attachment. Status goes draft → submitted and the approval chain is created.
  5. Track itScholar · /student/submissions See the stage-by-stage approval trail, reviewer comments and the remarks thread.
  6. Revise if askedScholar On needs_revision, edit and resubmit — pending approvals are cleared and the chain restarts cleanly from stage 1.
  7. Pay the semester feeScholar · /student/fees The scholar sees amount, due date, status and payments recorded so far. Payment itself happens offline; the coordinator records it.
  8. Keep the research profile currentScholar · /student/profile/research Bio, interests, institution, ORCID, Scholar link, publications. Toggling public exposes it at /p/:slug — a genuine public URL, so treat it as publishing.

3c · The review chain

Scholar submits→ Stage 1 · Coordinator→ Stage 2 · Academic Guide→ Stage 3 · Industry Mentor→ Approved
  • Each stage opening emails exactly one party: approval_stage_opened to that stage's reviewer.
  • A reviewer may only act on a review assigned to them, or on an unassigned role-slot whose role they hold. There is no blanket admin override — an admin cannot rubber-stamp someone else's named stage.
  • Three actions: Approve (advances to the next stage, or finalises), Request revision (bounces to the scholar), Reject. Both reject and request-revision send the scholar the submission_needs_revision email.
  • Separately from the chain there is a remarks thread on every submission — any authorised reviewer can leave notes at any time without acting on their stage. Use this for coaching; use the stage action for decisions.
  • Optional assignments collapse the chain to a single coordinator approval. Mandatory ones use the batch's approval_config, defaulting to the three layers above.

3d · Semester rollover

This is the biggest hole in the lifecycle today. Every enrolment row carries batch_enrollments.current_semester, and the whole UI reads it — but nothing in the codebase ever writes it after enrolment. There is no endpoint, no button, no bulk action. A scholar who finishes Semester 1 stays on Semester 1 forever unless the row is edited in the database by hand. See G-01 for the proposed fix.

The rollover that should happen at the end of each semester:

  1. Confirm every mandatory Semester N assignment is approved (or formally waived).
  2. Confirm every Semester N progress milestone is completed.
  3. Confirm the Semester N fee is paid or waived.
  4. Advance current_semester to N+1 for the batch (or for selected scholars).
  5. Publish Semester N+1 assignments, fees and milestones.
  6. Announce the new semester to the batch from /admin/notifications.

Phase 4 — Completion and exit

  1. Final submission approvedChain The last mandatory Semester 4 submission clears all stages.
  2. All dues clearedCoordinator · /admin/fees No fee row left in pending or overdue.
  3. Enrolment marked completedCoordinator · /admin/students Set batch_enrollments.status = completed via the bulk action on the students page. Partial — completion is a status flip; there is no completion certificate, transcript export or exit checklist yet (G-07).
  4. Batch closedAdmin · /admin/batches Set the batch to completed once every scholar in it is done.
  5. Public research profile stays liveAlumnus /p/:slug keeps working — it is the lasting artefact of the fellowship.

2 · Role-wise SOPs

Each SOP is written so it can be handed to one person as their entire job description on this system. Give a new joiner only their own section plus Section 1.

A

SOP · Administrator

System owner. Configures everything, owns the data, unblocks everyone else. 1–2 people, never more.

What only you can do

  • Create and edit users, and assign or revoke roles (/admin/users, /admin/roles).
  • Change what any role is allowed to do, and at what scope (/admin/roles).
  • Global settings: email credentials, branding, UI labels (/admin/settings).
  • Edit the email template library (/admin/email-templates).
  • Read the audit log of every create/update/delete in the system (/admin/audit-logs).
  • Bulk-import assignment submissions on behalf of scholars (admin-only endpoint).
  • Reset any user's password.

First-week SOP (do in this order)

  1. Verify email delivery/admin/settings Save the Brevo key, send a test to yourself, confirm mode is live not mock. If it says mock, the server .env has no SMTP credentials — no candidate will ever receive a password.
  2. Brand and label/admin/settings Logos (light + dark) and the student/scholar wording.
  3. Course → Batch → Workflow/admin/wizard Create the course with its fee map, create the batch, then set the batch's approval workflow before anyone can submit anything.
  4. People/admin/users → /admin/roles Create the coordinator first, scoped to the course. Then guides and mentors, scoped to the batch. Send credentials. Ask each to log in and confirm their menu looks right.
  5. Notification rules/admin/wizard → Notifications Decide who gets staff alerts. If you leave this default, staff alerts go to coordinators and admins.
  6. Dry runAll screens Before real candidates: apply as a fake candidate, shortlist, send the test, take the test, shortlist finally, mark paid, convert, log in as that scholar, submit an assignment, and approve it through all three stages. If any step surprises you, fix it before go-live — not after.

C

SOP · Coordinator

The engine of the program. Runs admissions end-to-end, then runs the academic calendar for every batch in the course.

Your menu

Applicants · Students · Batches · Formats · Progress Reports · Assignments · Submissions · Approvals · Fees · Media · Test Builder · Notifications. No Users, Roles, Settings or Audit Logs — that is correct, not a bug.

Admissions SOP

  1. Work the board, not the list/admin/applicants → Kanban The Kanban is stage-aware: each column offers exactly the actions valid at that stage, so you cannot skip a step by accident. Use the list view only for search and export.
  2. Applied → screen within 48 hours Open each card, check PhD completion, discipline, publications and the research statement. Shortlist for test, or reject with a real remark (the remark is permanent and is the official reason).
  3. Shortlisted for Test → send in batches Send the test to the whole column at once where possible. Confirm the emails actually went — the toast tells you the send count.
  4. Test Sent → chase, don't wait Use the column's bulk reminder for anyone who hasn't started. Watch for the Test in progress badge; only use Reset attempt for a genuine technical failure, and note why in the candidate's record.
  5. Test Submitted → evaluate descriptive answers Auto-scoring covers MCQ and true/false only. Open the test-results screen and award marks on short/long answers before making a shortlist decision.
  6. Final Shortlist → the fee letter goes automatically Moving a candidate here sends the registration-fee email by itself. Do not also send it manually. Use the bulk payment reminder (24-hour cooldown) as the deadline approaches.
  7. Reconcile payments daily Against the bank statement, tick candidates and mark paid. This is manual and it is your responsibility — no gateway does it for you.
  8. Convert, then immediately complete the onboarding checklist Conversion is not onboarding. Straight after converting: send credentials, assign the academic guide and industry mentor, create the Semester 1 fee, create the Semester 1 milestones. A scholar without guides will stall at their first submission.

Academic SOP (per semester)

  1. Publish assignments for the batch with correct semester, due date and mandatory flag.
  2. Raise fee rows for every active scholar for that semester.
  3. Create progress milestones per scholar.
  4. Upload the semester's formats and lectures.
  5. Clear your approvals queue at least twice a week — you are stage 1, so you are the bottleneck for the entire chain.
  6. At semester end, run the rollover checklist and announce the next semester to the batch.
Course switcher. If you run more than one course, the header switcher sets the course context that every list obeys. Empty screens are almost always the wrong course selected — check the switcher before reporting a bug.
G

SOP · Academic Guide

Internal faculty supervisor. Stage 2 of the approval chain. Sees only the scholars assigned to them.

Your menu

Students · Submissions · Approvals · Progress Reports · Assignments (read) · Media (read) · Notifications. Everything is scoped to your batch and your scholars.

  1. Log in and open Approvals/admin/approvals This is your work queue. A row appears here when the coordinator has approved a submission and your stage has opened. You also get the approval_stage_opened email.
  2. Read the submission properly/admin/submissions Open the attachment, read the content, check it against the published format and the assignment brief. Check the remarks thread for what earlier reviewers already said.
  3. Coach in remarks, decide in the stage action Leave detailed feedback as a remark — it stays with the submission and the scholar sees it. Then take exactly one stage action.
  4. Approve / Request revision / Reject Approve passes it to the Industry Mentor. Request revision returns it to the scholar and restarts the chain on resubmission — always write a comment saying what to change. Reject is for work that should not be resubmitted in its current form.
  5. Track your scholars' progress/admin/students/:id, /admin/progress Check milestone completion percentages between submissions, not only at deadlines.
You cannot act on someone else's stage. If an approval row does not appear in your queue, it is either not yet your turn or you are not the assigned guide for that scholar. Ask the coordinator to check the guide assignment — do not ask an admin to approve it for you; the system deliberately forbids that.

Service level

Recommended: act on any open stage within 5 working days. Everything downstream — the mentor's review, the scholar's semester progress, the rollover — waits on you.

M

SOP · Industry Mentor

External industry supervisor. The final approval stage. Read-only everywhere except their own approval action.

Your menu

Students (read) · Submissions (read) · Approvals (act) · Progress Reports (read) · Notifications. You deliberately cannot edit submissions, fees, assignments or any scholar record.

  1. Watch for the review email You are notified only when stage 3 opens for one of your scholars — coordinator and guide have already passed it.
  2. Review for applied/industry relevance/admin/approvals Your lens is different from the guide's: practical applicability, industry validity of the method, usefulness of the conclusions.
  3. Take the final action Approve marks the whole submission approved and emails the scholar. Request revision sends it back to the scholar and the chain restarts from stage 1 on resubmission — use it deliberately, it costs the scholar a full cycle.
  4. Leave a remark, always A one-line remark on approval is worth more to the scholar than a silent green tick.
S

SOP · Scholar (Student)

The enrolled fellow. Two years, four semesters, one portal.

Your menu

Dashboard · Assignments · My Submissions · Formats · Progress Reports · Fees · My Profile · Research Profile · Lectures · Notifications.

Week one

  1. Log in and change your password/login → /student/profile Use the credentials emailed to you. Change the password immediately.
  2. Complete your profile/student/profile Contact details and photo. Staff use this to reach you.
  3. Build your research profile/student/profile/research Bio, research interests, institution, designation, ORCID, Google Scholar, LinkedIn, and your publications. Set it public only when you are happy for the world to read it — it becomes a live page at /p/your-slug.
  4. Read the notice board/student/notifications Announcements, Zoom links and due-date reminders all land here as well as in your inbox.

Every semester

  1. Check Assignments first/student/assignments Every published assignment for your batch, with its semester, due date, whether it is mandatory, and your current submission status.
  2. Download the format before you write/student/formats
  3. Watch the lectures/student/lectures
  4. Submit — once/student/assignments → Submit You get one submission per assignment. Attach the file and click Submit for review. A progress report will not submit without an attachment.
  5. Follow the review/student/submissions Coordinator → Academic Guide → Industry Mentor. You can see which stage is open and every comment.
  6. Revise fast On needs revision, fix and resubmit. The chain restarts at stage 1, so a slow revision costs you the full review cycle again.
  7. Pay the fee before the due date/student/fees Reminders start 7 days out. Payment happens offline; your coordinator records it and the status turns paid. If you have paid and it still says pending, tell the coordinator — the system cannot see your bank.
  8. Keep progress milestones moving/student/progress Your guide reads these between submissions.
Golden rules for scholars. One submission per assignment · always draft on the current format · a revision restarts the whole chain · your research profile is public the moment you toggle it.
?

SOP · Applicant (Candidate)

Not a user of the portal. Touches exactly three screens, then either becomes a scholar or does not.

  1. Apply/apply Complete the multi-step form: personal details, academic record (PhD university, year, discipline, thesis title, Scopus publications), and research statement. You get a confirmation email with a reference ID.
  2. Wait for the test invitation If shortlisted, you receive an email with a login link, username, password, test duration and the section list. Keep that email — it is your only credential.
  3. Take the entrance test/test-login Log in, read the instructions page, then start. The clock starts when you click start and does not stop. Answers autosave. Submit before the timer ends. You get a confirmation email with your score where applicable.
  4. If finally shortlisted You receive the interview-qualification letter with the registration fee amount and bank details. Pay before the stated deadline and inform the office.
  5. On enrolment You receive a fresh set of portal credentials — different from your test credentials — and you are now a scholar. Go to the scholar SOP.
If you are locked out mid-test — browser crash, power cut, network drop — contact the program office immediately. Only a coordinator can reset the attempt, and only within a sensible window.

6 · Lifecycle gap audit

Findings from reading the route tree, the RBAC layer, the schema and every module service. Ranked by what will break a real 2-year cohort soonest. P0 = the lifecycle cannot complete without it. P1 = it will complete, but staff will do painful manual work and mistakes will happen. P2 = polish and reporting.

P0 — must exist before real users

G-01 · No way to advance a scholar to the next semester Missing

Evidence. batch_enrollments.current_semester is created with a default of 1 and read in several places (student profile view, imports, exports), but a repository-wide search finds no UPDATE statement and no endpoint that ever changes it. The only writes are at insert time (conversion, bulk import, dev seed).

Consequence. A 4-semester program permanently stuck on Semester 1. Every semester-scoped list — assignments, fees, progress, submissions — drifts out of alignment with reality, and no report of "who is in which semester" is trustworthy.

Proposed fix.

  • Backend: POST /batches/:id/advance-semester — body { to_semester, student_user_ids? }. Guard with batches:update. Bump current_semester, write an audit entry, and enqueue a batch announcement.
  • Backend: PATCH /students/:id/semester for a single-scholar correction (a scholar who is held back or accelerated).
  • Frontend: a Promote to Semester N+1 button on /admin/batches/:id/students with a confirmation modal listing who will move, plus a per-scholar override on the profile page.
  • Optional guardrail: warn (do not block) when a scholar has unpaid fees or unapproved mandatory assignments in the current semester.
G-02 · Fees are not generated from the course fee structure Partial

Evidence. courses.fee_structure stores the per-semester amounts ({"1":50000,…}) and bulkCreateFees() exists in fees.service.js — but no route exposes it. The only fee creation path is POST /fees, one row for one scholar.

Consequence. For a 30-scholar batch across 4 semesters that is 120 fee rows created by hand, each an opportunity to fumble an amount or a due date. Fee reminders then fire on wrong data.

Proposed fix. Expose POST /fees/bulk (batch + semester + due date, amount defaulted from the course fee structure, applied to all active enrolments, idempotent so re-running does not duplicate). Add a Generate semester fees action on /admin/fees. Ideally chain it to G-01 so promoting a semester offers to raise that semester's fees.

G-03 · Onboarding does not enforce guide assignment Missing

Evidence. submitForReview() resolves the academic-guide and industry-mentor stages from student_guides. If no active guide exists, resolvedReviewerId is null and the approval row is inserted anyway with a null reviewer and, for student_guide-type stages, no reviewer_role fallback either.

Consequence. The submission passes coordinator approval and then sits in a stage no-one can see or action. It appears in nobody's queue. Silent, and only discovered when a scholar complains weeks later.

Proposed fix. Three layers: (1) block conversion-to-scholar from being marked complete until both guides are assigned, or surface a persistent "needs guides" flag on the student list; (2) at submit time, if a student_guide stage cannot resolve, fall back to reviewer_role so a coordinator/admin can act, and notify staff; (3) add an Unassigned reviewer filter to /admin/approvals so stalls are visible.

G-04 · No semester/lifecycle state machine — statuses can be skipped Partial

Evidence. updateApplicantStatus() accepts any target status with no transition validation. The Kanban UI is disciplined about which buttons it shows, but the API is not — and the list view and bulk actions share the same endpoint.

Consequence. A candidate can reach payment_received without ever having a test attempt, or enrolled without a recorded fee. Pipeline metrics stop meaning anything.

Proposed fix. Define the allowed transition map server-side (forward moves, plus the explicit corrections the UI already offers, plus reject-from-anywhere and reconsider) and reject the rest with a clear 400. Same treatment for submission_status and enrollment_status.

P1 — will cause daily pain

IDGapEvidenceFix
G-05No bulk progress-milestone creation Partial POST /progress-reports takes exactly one scholar, one module. A 30-scholar batch with 5 milestones per semester = 150 manual creations per semester. Add POST /progress-reports/bulk (batch + semester + list of module templates) and a per-course milestone template set, so a semester's milestones are created in one action.
G-06No fee receipt output Missing fee_payments.receipt_url is stored but nothing generates a receipt. @react-pdf/renderer is already a dependency. Generate a PDF receipt on payment record; attach it to the fee row and email it to the scholar.
G-07No completion / exit flow Missing Completion is a status flip on the enrolment row. No certificate, no transcript, no exit checklist, no "all requirements met" validation. Add a completion checklist view per scholar (all 4 semesters: fees clear, mandatory assignments approved, milestones complete), then a generated completion certificate PDF.
G-08Approval chain has no reassignment or escalation Missing Only the assigned reviewer or a matching role-slot holder can act, and there is deliberately no admin override. If a guide leaves, resigns or goes silent, the submission is stuck permanently. Add an admin-only Reassign reviewer action on an approval row (fully audit-logged, which preserves the integrity the current rule is protecting), plus an SLA-breach report of stages open longer than N days.
G-09Test evaluation is half-manual with no queue Partial MCQ and true/false auto-score. Short/long/file-upload answers need manual marks per question, but there is no "tests awaiting evaluation" queue — you must open candidates one by one. Add an evaluation queue filtered to attempts with unscored descriptive responses, and show evaluated_at / evaluator on the applicant card.
G-10Onboard route is orphaned Partial /onboard is routed in App.jsx, but no backend endpoint or email links to it. Conversion issues a generated password instead of an invite link. Either wire it up as a proper first-login set-password flow (token-based invite, and drop the generated-password email), or remove the route so it cannot confuse anyone.
G-11Registration fee is not a fee record Partial The admission registration fee lives only as the applicant status payment_received — amount, date and reference are never captured anywhere. Capture amount / date / transaction reference when marking paid, and carry it into the scholar's fee ledger on conversion so the financial record is continuous from application to completion.

Pre-flight checklist before any training session

  • Email is in live mode and a test message has actually arrived in an inbox.
  • A demo course, demo batch and a published demo test exist, separate from real data.
  • Each trainee has their own account with the real role they will hold — never train on a shared admin login.

  • Someone is nominated as the day-one support contact, and the trainees know who it is.
